D1 Keep the multi-agent architecture保留多智能体架构 Decided 已定 ▶ Is it over-built? No — the shape is right. 过度设计了吗？没有 —— 形态是对的。

Context 背景

Concern that four-plus agents, hybrid retrieval, a reranker, Langfuse and Ragas might be more machinery than Phase 1 needs. 担心四个以上的智能体、混合检索、重排序器、Langfuse、Ragas 对第一阶段来说机器太多、过度工程。

Resolution 结论

Keep every agent. The design is right-shaped: each agent needs different tools and context, and the Verifier must be independent of the Writer. Supervisor, Researcher, Matcher and Verifier genuinely reason and loop. Analyst and Writer are closer to tool calls, but keeping them as graph nodes is fine. 保留全部智能体。设计的形态是对的：每个智能体需要不同的工具与上下文，而校验员必须独立于撰写员。主管、研究员、匹配器、校验员是真正在推理和循环的。分析员和撰写员更接近一次工具调用，但作为图节点保留没问题。

Why 为什么. "Over-built" here is about timing, not shape — the risk is building all the surface area before anything runs end to end. The milestone order (ingest → retrieval → agents → matcher → eval) already mitigates that. The goal of relying on agents to analyze and do different jobs is legitimate and preserved. 这里的"过度"是时机问题，不是形态问题 —— 风险在于还没跑通端到端就铺开太多工作面。里程碑顺序（采集→检索→智能体→匹配→评估）已经缓解了这一点。"靠智能体来分析、各司其职"这个目标是合理的，并且被保留了下来。
D2 How the Financial Analyst fetches numbers财务分析员如何取数字 Decided → C 已定 ▶ Hybrid: safe tools for core metrics, SQL fallback for the rest. 混合：核心指标走安全工具，其余用 SQL 兜底。

Context 背景

The Analyst needs figures out of Postgres. How it gets them decides whether the financial numbers are trustworthy. XBRL is messy — one filer calls revenue Revenues, another RevenueFromContractWithCustomerExcludingAssessedTax, plus restatements and duplicate rows. 分析员需要从 Postgres 取数字。取数的方式决定了财务数据是否可信。XBRL 很乱 —— 有的公司营收字段叫 Revenues，有的叫 RevenueFromContractWithCustomerExcludingAssessedTax，还有财报重述和重复行。

Options considered 备选方案

A · Free-form text-to-SQL 自由生成 SQL
Flexible — answers questions you never anticipated. 灵活，能答预料之外的问题。 LLM often writes SQL that runs fine but returns the wrong number — the worst failure for a cited, trust-first brief. LLM 常写出"能跑但取错数"的 SQL —— 对信任优先的带引用简报是最糟的失败。
B · Parameterized query tools 参数化查询工具
Safe and reliable; XBRL normalization lives in tested Python. 安全可靠；XBRL 规整逻辑放在经过测试的 Python 里。 Exact-match eval becomes meaningful; still a real agent (reasons over results). 精确匹配评估才有意义；它仍是真智能体（对结果做推理）。 Only answers questions the functions support. 只能回答函数支持的问题。
C · Hybrid 混合Chosen 已选
Parameterized tools for core metrics (revenue, R&D, margins — the eval set). 核心指标（营收、研发、利润率 —— 即评估集）走参数化工具。 Text-to-SQL kept as a fallback for unusual open-ended questions. 开放式冷门问题用 text-to-SQL 兜底。 Best of both; a little more to build than B alone. 两者兼得；比只做 B 多一点工作量。
Why C 为什么选 C. Keeps the Analyst a real reasoning agent while moving the error-prone part out of the LLM for the figures that matter most. Protects the cited financials and keeps the golden-set exact-match eval meaningful. Built at Milestone 3 (tools/sql_tools.py), not now. 让分析员保持为真正会推理的智能体，同时把最关键数字的"易错部分"从 LLM 手里拿走。保护带引用的财务数据，并让标准答案集的精确匹配评估仍然有意义。在里程碑 3 实现（tools/sql_tools.py），现在还不做。
D3 Embedding model & pgvector dimension嵌入模型与向量维度 Open 待定 ▶ Fixes the schema column; decide before Milestone 2. 它决定了表结构的列；需在里程碑 2 前定下。

Context 背景

The schema hardcodes embedding vector(1536). The embedding model sets that number, so it should be chosen before the chunking/embedding work starts. 表结构里写死了 embedding vector(1536)。这个维度由嵌入模型决定，所以应在切块/嵌入工作开始前选好。

Options on the table 备选

OpenAI text-embedding-3-small
1536 dims — matches the schema. Cheap, good, needs an API key. 1536 维，与现有表结构一致。便宜、够用，需要 API key。
OpenAI text-embedding-3-large
3072 dims — higher quality and cost; schema changes. 3072 维，质量与成本更高；需改表结构。
Local / open (bge) 本地开源
No per-call cost, but needs torch and a model download; dimension varies. 无单次调用费用，但需 torch 和下载模型；维度随模型而定。
Status 状态. Awaiting your call. No blocker until Milestone 2. 等你决定。里程碑 2 之前不构成阻塞。
