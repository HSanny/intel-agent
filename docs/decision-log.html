Where we are · 当前进度

It is not yet an agent: there's no LLM reasoning or orchestration. The agents (LangGraph supervisor, researcher, analyst, writer) arrive at Milestone 3. D1 Keep the multi-agent architecture保留多智能体架构 Decided 已定 ▶ Is it over-built? No — the shape is right. 过度设计了吗？没有 —— 形态是对的。

Context 背景

Concern that four-plus agents, hybrid retrieval, a reranker, Langfuse and Ragas might be more machinery than Phase 1 needs. 担心四个以上的智能体、混合检索、重排序器、Langfuse、Ragas 对第一阶段来说机器太多、过度工程。

Resolution 结论

Keep every agent. The design is right-shaped: each agent needs different tools and context, and the Verifier must be independent of the Writer. Supervisor, Researcher, Matcher and Verifier genuinely reason and loop. Analyst and Writer are closer to tool calls, but keeping them as graph nodes is fine. 保留全部智能体。设计的形态是对的：每个智能体需要不同的工具与上下文，而校验员必须独立于撰写员。主管、研究员、匹配器、校验员是真正在推理和循环的。分析员和撰写员更接近一次工具调用，但作为图节点保留没问题。

Why 为什么. "Over-built" here is about timing, not shape — the risk is building all the surface area before anything runs end to end. The milestone order (ingest → retrieval → agents → matcher → eval) already mitigates that. The goal of relying on agents to analyze and do different jobs is legitimate and preserved. 这里的"过度"是时机问题，不是形态问题 —— 风险在于还没跑通端到端就铺开太多工作面。里程碑顺序（采集→检索→智能体→匹配→评估）已经缓解了这一点。"靠智能体来分析、各司其职"这个目标是合理的，并且被保留了下来。
D2 How the Financial Analyst fetches numbers财务分析员如何取数字 Decided → C 已定 ▶ Hybrid: safe tools for core metrics, SQL fallback for the rest. 混合：核心指标走安全工具，其余用 SQL 兜底。

Context 背景

The Analyst needs figures out of Postgres. How it gets them decides whether the financial numbers are trustworthy. XBRL is messy — one filer calls revenue Revenues, another RevenueFromContractWithCustomerExcludingAssessedTax, plus restatements and duplicate rows. 分析员需要从 Postgres 取数字。取数的方式决定了财务数据是否可信。XBRL 很乱 —— 有的公司营收字段叫 Revenues，有的叫 RevenueFromContractWithCustomerExcludingAssessedTax，还有财报重述和重复行。

Options considered 备选方案

A · Free-form text-to-SQL 自由生成 SQL
Flexible — answers questions you never anticipated. 灵活，能答预料之外的问题。 LLM often writes SQL that runs fine but returns the wrong number — the worst failure for a cited, trust-first brief. LLM 常写出"能跑但取错数"的 SQL —— 对信任优先的带引用简报是最糟的失败。
B · Parameterized query tools 参数化查询工具
Safe and reliable; XBRL normalization lives in tested Python. 安全可靠；XBRL 规整逻辑放在经过测试的 Python 里。 Exact-match eval becomes meaningful; still a real agent (reasons over results). 精确匹配评估才有意义；它仍是真智能体（对结果做推理）。 Only answers questions the functions support. 只能回答函数支持的问题。
C · Hybrid 混合Chosen 已选
Parameterized tools for core metrics (revenue, R&D, margins — the eval set). 核心指标（营收、研发、利润率 —— 即评估集）走参数化工具。 Text-to-SQL kept as a fallback for unusual open-ended questions. 开放式冷门问题用 text-to-SQL 兜底。 Best of both; a little more to build than B alone. 两者兼得；比只做 B 多一点工作量。
Why C 为什么选 C. Keeps the Analyst a real reasoning agent while moving the error-prone part out of the LLM for the figures that matter most. Protects the cited financials and keeps the golden-set exact-match eval meaningful. Built at Milestone 3 (tools/sql_tools.py), not now. 让分析员保持为真正会推理的智能体，同时把最关键数字的"易错部分"从 LLM 手里拿走。保护带引用的财务数据，并让标准答案集的精确匹配评估仍然有意义。在里程碑 3 实现（tools/sql_tools.py），现在还不做。
D3 Embedding model & pgvector dimension嵌入模型与向量维度 Decided 已定 ▶ Local bge-small-en-v1.5 / 384, swappable; fine-tune later. 本地 bge-small-en-v1.5 / 384，可替换；后续微调。

Context 背景

The schema hardcodes embedding vector(1536). The embedding model sets that number, so it should be chosen before the chunking/embedding work starts. 表结构里写死了 embedding vector(1536)。这个维度由嵌入模型决定，所以应在切块/嵌入工作开始前选好。

Options on the table 备选

OpenAI text-embedding-3-small
1536 dims — matches the schema. Cheap, good, needs an API key. 1536 维，与现有表结构一致。便宜、够用，需要 API key。
OpenAI text-embedding-3-large
3072 dims — higher quality and cost; schema changes. 3072 维，质量与成本更高；需改表结构。
Local / open (bge) 本地开源Chosen 已选
bge-small-en-v1.5, 384-dim. Hands-on, offline, free per call; needs torch + model download; slower on CPU. bge-small-en-v1.5，384 维。动手、离线、无调用费；需 torch 与下载模型；CPU 较慢。
Decision 决定. Local bge-small-en-v1.5 (384-dim) via sentence-transformers, behind a swappable EmbeddingProvider interface (OpenAI kept as an alternate). Chosen for hands-on learning and a later fine-tuning track. Changing the model later = swap provider + recreate the table at the new dimension + re-embed. 本地 bge-small-en-v1.5（384 维），经 sentence-transformers，藏在可替换的 EmbeddingProvider 接口后（OpenAI 作为备选）。为动手学习与后续微调track而选。以后换模型 = 换 provider + 按新维度重建表 + 重新嵌入。

D6 Lexical (BM25) ranker词法（BM25）排序器 Decided 已定 ▶ rank_bm25 — true BM25, fully inspectable. rank_bm25 —— 真正的 BM25，完全可见。

Context 背景

The hybrid search needs a keyword side alongside the dense vectors. Two ways to get BM25-style lexical ranking. 混合检索在稠密向量之外还需要一个关键词侧。获得 BM25 式词法排序有两种方式。

Options considered 备选方案

rank_bm25Chosen 已选
Pure-Python, literally BM25 — the TF/IDF math is visible. Great for learning. 纯 Python，就是 BM25 —— TF/IDF 计算可见，适合学习。 Builds the index in memory per query (fine for a tiny corpus, not for scale). 每次查询在内存建索引（小语料没问题，大规模不行）。
Postgres full-text (ts_rank)
In-DB, scales better, but ts_rank ≠ true BM25. Can swap in later. 在库内、更易扩展，但 ts_rank 不是真正的 BM25。以后可替换。
Why rank_bm25 为什么选它. Transparency for the learning goal; the corpus is tiny so the in-memory cost is irrelevant. Swap to Postgres FTS or pg_search if scale ever matters. 为学习目标选择透明度；语料很小，内存成本无关紧要。将来需要扩展再换成 Postgres FTS 或 pg_search。

How it's built · 逐步构建与学习

The Milestone 2 retrieval pipeline, step by step — what each part does, the trade-offs, and what we chose. A query flows top to bottom. Click a step to expand. 里程碑 2 的检索流水线，逐步讲解 —— 每一部分做什么、取舍、以及我们的选择。一次查询自上而下流动。点击展开。

S1 Chunking切块 word-window ▶ Split long filings into overlapping passages.把长文件切成有重叠的段落。

A 10-K is far too long to embed or read whole, so each item section is cut into ~400-word windows that overlap by 60 words. The overlap keeps a fact that straddles a boundary from being split away. Code: ingest/chunk_embed.py.10-K 太长，无法整体嵌入或阅读，于是把每个条目章节切成约 400 词、相互重叠 60 词的窗口。重叠能避免跨边界的事实被切散。代码：ingest/chunk_embed.py。

Trade-offs 取舍

Simple, testable, predictable size. 简单、可测、大小可控。 Can cut mid-sentence; word count only approximates tokens. 可能从句中切断；词数只是近似 token。 Alternatives: sentence/semantic-aware (cleaner, more complex), token-exact via tiktoken. 备选：按句/语义（更干净、更复杂）、用 tiktoken 精确切 token。
S2 Embeddings嵌入 bge-small · 384d ▶ Turn each passage into a 384-number meaning vector.把每个段落变成 384 维的"含义"向量。

An embedding model maps text to a vector so that similar meanings land near each other. We run bge-small-en-v1.5 locally via sentence-transformers, normalize the vectors (so cosine similarity = dot product), and prepend a short instruction to queries (a bge convention that improves retrieval). Code: embeddings/local_bge.py.嵌入模型把文本映射为向量，使含义相近的文本彼此靠近。我们用 sentence-transformers 在本地跑 bge-small-en-v1.5，对向量归一化（使余弦相似度=点积），并给查询加一句简短指令（bge 的惯例，可提升检索）。代码：embeddings/local_bge.py。

Why local 为什么本地

Hands-on, offline, no per-call cost; you see batching/pooling/vectors. 动手、离线、无调用费；能看到批处理/池化/向量。 Needs torch + a model download; slower on CPU than an API. 需 torch 与下载模型；CPU 上比 API 慢。 Swappable: EmbeddingProvider interface lets us A/B OpenAI or a fine-tuned model later. 可替换：EmbeddingProvider 接口便于以后对比 OpenAI 或微调模型。
S3 Vector search向量检索 pgvector · HNSW ▶ Find passages whose meaning is nearest the query.找出含义与查询最接近的段落。

Vectors live in Postgres via the pgvector extension. A search embeds the query and finds the nearest chunks by cosine distance (the <=> operator); score = 1 − distance. An HNSW index makes this approximate-but-fast instead of scanning every row. Code: store/db.py, retrieval/vector.py.向量通过 pgvector 扩展存在 Postgres 里。检索时先嵌入查询，再按余弦距离（<=> 运算符）找最近的分块；分数 = 1 − 距离。HNSW 索引让它"近似但快"，而不必扫描每一行。代码：store/db.py、retrieval/vector.py。

Strength / limit 优点 / 局限

Catches meaning and synonyms, not just exact words. 抓住含义与同义，不只是字面。 Can miss exact terms — a ticker, a defined word, a number. 可能错过精确词 —— 代码、定义术语、数字。
S4 BM25 keyword searchBM25 关键词检索 rank_bm25 ▶ Classic lexical ranking — the exact-word complement.经典词法排序 —— 精确词的互补。

BM25 scores a passage by how often the query's terms occur in it, weighted down for terms common across the whole corpus (inverse document frequency). So a rare, specific word counts for more than a common one. This catches the exact matches the dense model smooths over. Code: retrieval/bm25.py.BM25 按查询词在段落中出现的频次打分，并对全语料中常见的词降权（逆文档频率）。因此稀有、具体的词比常见词更重要。这能抓住稠密模型会"抹平"的精确匹配。代码：retrieval/bm25.py。

Decision 决策

D6: rank_bm25 (true BM25, fully visible) over Postgres ts_rank. D6：选 rank_bm25（真正的 BM25、完全可见），而非 Postgres 的 ts_rank。
S5 Hybrid fusion (RRF)混合融合（RRF） RRF · k=60 ▶ Merge the two rankings into one, fairly.把两种排序公平地合成一个。

Dense and BM25 each surface good-but-different results, and their raw scores live on different scales — so we can't just add them. Reciprocal Rank Fusion uses only the rank a passage got in each list: fused score = Σ 1 / (k + rank), with k=60. A passage that ranks well in both beats one that tops only a single list. Code: retrieval/hybrid.py.稠密与 BM25 各自给出"好但不同"的结果，且原始分数量纲不同 —— 不能直接相加。倒数排名融合（RRF）只用段落在每个列表中的名次：融合分 = Σ 1 / (k + 名次)，k=60。在两边都靠前的段落，胜过只在一边第一的段落。代码：retrieval/hybrid.py。

Why it's nice 妙处

No score calibration needed; robust and simple; one pure function (unit-tested). 无需分数校准；稳健简单；一个纯函数（已单测）。
S6 Reranking重排序 cross-encoder ▶ A slower, sharper second pass over the top candidates.对头部候选做更慢更准的二次排序。

Retrieval uses a bi-encoder: query and passage are embedded separately, so the model never sees them together. A cross-encoder reads the (query, passage) pair jointly and scores relevance directly — more accurate, but too slow to run over everything. So we run it only on the top fused hits, to reorder them. Code: retrieval/rerank.py (bge-reranker-base, local; a Noop reranker is used in tests).检索用的是双编码器：查询和段落分别嵌入，模型从不同时看它们。交叉编码器把（查询，段落）一起读入并直接给相关性打分 —— 更准，但太慢，不能对全部跑。因此只对头部融合结果重排。代码：retrieval/rerank.py（bge-reranker-base，本地；测试用空操作重排器）。

This is also a natural thing to fine-tune later (see D7). 这也是以后适合微调的一环（见 D7）。
S7 Citations引用 filing_search ▶ Every passage traces back to its exact filing + date.每个段落都能追溯到具体文件与日期。

Each chunk carries its accession_no, item and chunk_idx, joined to the company's ticker, form and filing date. The filing_search tool returns every passage wrapped in a Citation, so the Researcher agent (M3) — and you — can trace each claim to the exact filing section and date. This is what makes the system trust-first. Code: tools/filing_search.py.每个分块都带着自己的 accession_no、item、chunk_idx，并关联到公司的代码、表单和提交日期。filing_search 工具把每个段落包进一个 Citation 返回，于是研究员 agent（M3）—— 以及你 —— 都能把每条结论追溯到具体的文件章节与日期。这正是系统"信任优先"的根基。代码：tools/filing_search.py。
